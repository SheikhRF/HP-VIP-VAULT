## Commands

All commands run from `hp-vip-vault/` (the Next.js app root, one level below the repo root).

```bash
npm run dev      # start dev server (Turbopack)
npm run build    # production build (Turbopack)
npm run start    # run the production build
npm run lint      # eslint .
```

There is no test suite/framework configured in this project (no test script in `package.json`). The two exceptions are framework-free regression scripts (plain assertions, no deps, same `npx tsx scripts/<name>.ts` pattern):
- `npx tsx scripts/test-admin-claims.ts` — admin role-claim casing logic in `lib/auth/requireAdmin.ts`. Run after touching that file or any admin-check code.
- `npx tsx scripts/test-driver-claims.ts` — driver/admin role-claim logic (`isDriverOrAdminClaims`) in `lib/auth/requireAdmin.ts`. Run after touching that file or any driver-check code.
- `npx tsx scripts/test-dvla-sync-logic.ts` — retry/backoff and concurrency-limiter logic in `lib/dvla/syncFleet.ts` / `lib/dvla/concurrencyLimiter.ts`. Run after touching DVLA sync code.
- `npx tsx scripts/test-car-status-logic.ts` — the shared "needs attention / driveable" logic in `lib/cars/status.ts`. Run after touching car compliance/status code.

One-off migration script (not part of the app build): `npx tsx scripts/sync-clerk-users.ts` — backfills Clerk users into the Supabase `profiles` table. Requires `CLERK_SECRET_KEY`, `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SECRET_KEY` in `.env.local`.

`npm run lint` works (not blocked by anything). The large pre-existing `@typescript-eslint/no-explicit-any`/unused-import backlog (~45 issues, previously scattered across admin forms, API routes, and `Hyperspeed.tsx`) has been cleaned up — `npm run lint` now reports only 8 small pre-existing problems (`react/no-unescaped-entities` in `app/about/page.tsx`, `@next/next/no-img-element` in a few admin forms, `react-hooks/exhaustive-deps` in `Hyperspeed.tsx`/`Reveal.tsx`), none of them `any`/unused-import. `tsc --noEmit` and the build are clean. Any *new* lint issue you introduce should still be fixed, not folded into that remaining pre-existing debt.

## Architecture

**Stack:** Next.js 16 App Router + React 19 + TypeScript (strict) + Tailwind v4 + shadcn/ui-style components (`components/ui/`). Auth via Clerk, data/storage via Supabase, external data from the DVLA Vehicle Enquiry Service and API Ninjas. Path alias `@/*` maps to the app root (`hp-vip-vault/`).

**Domain:** "Horsepower.VIP Vault" — a car-club fleet app. Drivers log/edit/delete their own trips/mileage against a shared fleet (`/trips`, `/trips/add`); admins manage the fleet (add/edit/delete cars, bulk-induct new cars, sync DVLA data) and users/roles (`user`/`driver`/`admin`).

**Data model** (confirmed directly against the Supabase project via a read-only catalog query — no migration files live in this repo, so this is the real schema, not inferred):
- `cars` — PK `car_id` (`int8`, identity). `make`/`model`/`registration`/~15 spec fields are nullable `varchar` (populated from API Ninjas via `SPEC_MAP` in `app/api/cars/route.ts`), plus `mot`/`tax_status`/`tax_due_date` from DVLA. `mileage`/`price` are `int8`. `pictures` is `text[]`. `last_synced_at`/`"Times Stamp"` (note the space in that column name — it's real, not a typo to "fix") are `timestamptz`. `service_date` is `date`. Only index is the PK.
- `trips` — PK `trip_id` (`int8`, identity). `car_id` is a real FK to `cars(car_id)` **ON DELETE CASCADE** — deleting a car deletes its trips. `user_id` is plain `text` with **no FK to `profiles`**. `mileage_before`/`mileage_after`/`rating` are `int4`; `start_date`/`end_date` are `date`; `notes` is `text`. DB-level check constraints: `trips_valid_dates` (`end_date` null or ≥ `start_date`) and `trips_valid_mileage` (`mileage_after` null or ≥ `mileage_before`) — the app-level validation in `app/api/trips/route.ts` duplicates these, but the DB enforces them regardless. Indexes: `car_id`, `user_id`, `start_date`.
- `profiles` — PK `id` (`text`, the Clerk user id). `email` is `text`, unique. `role` is `text`, default `'user'`, with a check constraint `role IN ('user','driver','admin')` — the DB itself rejects any other value. `updated_at` is `timestamptz`. Kept in sync by `app/api/webhooks/clerk/route.ts` on Clerk's `user.created`/`user.updated`/`user.deleted` events.
- Real scale as of the last check: 20 `cars`, 8 `trips`, 22 `profiles`, 35 objects in the `car-images` bucket — this is a small club fleet, not hundreds of rows; don't over-engineer for scale that doesn't exist yet.

**Role/auth model — the real mechanism, confirmed from the Clerk dashboard (not a guess):**
- `publicMetadata.role` on the Clerk user is the source of truth (plain lowercase string, `"user"`/`"driver"`/`"admin"`). The Clerk webhook normalizes it into `profiles.role` (which the DB also constrains to `'user'`/`'driver'`/`'admin'`). `driver` sits between `user` and `admin`: a driver can log trips (`/trips/add`) and edit/delete their own trips (`/trips`, `/trips/[id]/edit`); admins can do everything a driver can plus everything admin-only, via `isDriverOrAdminClaims()`/`requireDriverOrAdmin()` in `lib/auth/requireAdmin.ts` (unit-tested by `scripts/test-driver-claims.ts`) treating `admin` as a superset of `driver`. Trip ownership is checked against the *current* role, not history — a driver demoted back to `user` loses edit/delete rights on their own old trips too (see `app/api/trips/[id]/route.ts#canMutateTrip`).
- **`sessionClaims.role` and `sessionClaims.Role` are NOT the same claim with inconsistent casing — they are two different claims that happen to have similar names.** Clerk's session token has a default customization (Configure → Sessions → Customize session token) of `{ "role": "authenticated", "Role": "{{user.public_metadata.role}}", "FirstName": "{{user.first_name}}" }`. Lowercase `role` is a **Supabase-managed claim** added by Clerk's Supabase integration — it is hardcoded to the literal string `"authenticated"` for every signed-in user and has nothing to do with app roles; it will never equal `"admin"`. Capital `Role` is the actual app role, pulled from `public_metadata.role`. **There is no JWT template configured** — this mapping lives directly on the default session token.
- Despite the above, checking both `sessionClaims?.role === "admin"` and `sessionClaims?.Role === "admin"` (as `requireAdmin()`/`isAdminClaims()` in `lib/auth/requireAdmin.ts` and `proxy.ts` both do) is still correct and safe — the `role` half is just permanently a no-op, not a bug. **Use `requireAdmin()` from `lib/auth/requireAdmin.ts` for every admin-only check** — it returns a ready-to-return `NextResponse` on failure (`401` if not logged in, `403` if not admin): `const check = await requireAdmin(); if (!check.ok) return check.response;`. The underlying pure predicate `isAdminClaims()` is unit-tested by `scripts/test-admin-claims.ts`. There is no `lib/user/claims.ts#checkIsAdmin()` anymore — it was deleted (unused, single-case); don't reintroduce a second admin-check implementation.
- `proxy.ts` is this project's Next.js middleware (note the filename — it is the middleware, not a literal HTTP proxy). It enforces admin-ness for **page** routes matched by `isAdminRoute` (`/admin(.*)`, `/cars/add`), and separately enforces driver-or-admin-ness for `isDriverRoute` (`/trips`, `/trips/add`, `/trips/(.*)/edit`). It does **not** check admin/driver for any `/api/*` route — the generic API branch only requires a logged-in user. **Every API route that should be admin-only, driver-only, or owner-only must self-check inside the handler** (`requireAdmin()`/`requireDriverOrAdmin()` from `lib/auth/requireAdmin.ts`, or a manual ownership check like `app/api/trips/[id]/route.ts#canMutateTrip`). All current admin-facing API routes (`admin/mass-induct`, `admin/update-car`, `admin/sync-dvla`, `admin/sync-instagram`, `admin/trips`, `admin/users/[id]/role`, `cars/details`, `cars/trims`) already do this. `app/api/trips/route.ts`'s `GET` is the one intentional exception to the role-gating pattern: it only checks `auth()` for a logged-in `userId` (no driver/admin check), since it's filtered to the caller's own trips regardless of role — but its `POST` (logging a new trip) IS `requireDriverOrAdmin()`-gated.
- `proxy.ts`'s `isPublicRoute` also lists `/api/cron(.*)` alongside `/api/webhooks(.*)` — both bypass Clerk auth entirely at the middleware level because they authenticate themselves inside the handler instead (webhooks via Svix signature verification, cron routes via a `CRON_SECRET` bearer-token check). Any new cron-triggered route must live under `/api/cron/*` and do its own `Authorization: Bearer ${process.env.CRON_SECRET}` check — Vercel's cron invoker carries no Clerk session, so `requireAdmin()` cannot be used there.
- **Changing a user's role:** `app/api/admin/users/[id]/role/route.ts` (admin-gated) is the only place that should do this. It writes to **both** Clerk (`(await clerkClient()).users.updateUserMetadata(id, { publicMetadata: { role } })` — note `clerkClient` is an async function in this installed version, `await` it before use) and `profiles.role` directly in the same request, so the UI reflects the change immediately rather than waiting on the Clerk → webhook → `profiles` round-trip. Two UI entry points write to this route: `components/admin/RoleToggle.tsx` on the user detail page, and `components/admin/UserRowActions.tsx` inline on the `/admin/users` table row (added so admins don't have to open a user's detail page just to change their role).
- **Removing a user:** `app/api/admin/users/[id]/route.ts`'s `DELETE` handler (admin-gated) is the only place that should do this. It deletes the Clerk user (`client.users.deleteUser(id)`) then the `profiles` row in the same request, and rejects a request where the target id equals the calling admin's own id (no self-removal). `components/admin/UserRowActions.tsx` on `/admin/users` is the only UI entry point. Note: `trips.user_id` has no FK to `profiles`, so a removed user's trip history is left orphaned rather than cascade-deleted — this matches the existing DB design (see the `trips` schema note above), not a gap introduced by this route.
- **Changing a user's role:** `app/api/admin/users/[id]/role/route.ts` (admin-gated) is the only place that should do this. It writes to **both** Clerk (`(await clerkClient()).users.updateUserMetadata(id, { publicMetadata: { role } })` — note `clerkClient` is an async function in this installed version, `await` it before use) and `profiles.role` directly in the same request, so the UI reflects the change immediately rather than waiting on the Clerk → webhook → `profiles` round-trip. Accepts `"user"`/`"driver"`/`"admin"`. `components/admin/RoleToggle.tsx` on the user detail page is the only UI entry point for this — a 3-way segmented control (not a binary toggle), with per-transition `confirm()` copy.
- **Clerk is currently on the Development instance** (`pk_test_...` publishable key) while the app serves real production traffic on Vercel. The Clerk webhook endpoint is registered at `https://hp-vip-vault.vercel.app/api/webhooks/clerk`, subscribed to `user.created`/`user.updated`/`user.deleted`/`session.created` (the handler only acts on the three `user.*` events; `session.created` deliveries just fall through and return 200 — harmless, not a bug).

**Supabase access convention:** there is no shared Supabase client module in actual use. Every server page/route calls `createClient(process.env.NEXT_PUBLIC_SUPABASE_URL!, process.env.SUPABASE_SECRET_KEY!)` inline, using the service-role key to bypass RLS. (`lib/supabaseServer.ts` exists but is unused dead code — it only wraps the anon key and adds nothing over `lib/supabaseClient.ts`.) Follow the existing inline pattern rather than introducing a new shared client, unless asked to refactor it.

**RLS reality (confirmed from the Supabase dashboard — this matters for any new client-side Supabase query):**
- `cars`: RLS enabled, one policy — `SELECT` for the `anon` role only, `USING (true)`. No insert/update/delete policies at all (writes only ever go through server routes with the service-role key, which bypasses RLS anyway).
- `profiles`: RLS enabled, one policy — a user can `SELECT` their own row (`id = auth.jwt().sub`). No policy for anyone else or for writes.
- `trips`: **RLS enabled with zero policies.** Any request using the anon key gets nothing back — not an error, just an empty result.
- `car-images` storage bucket: no policies on `storage.objects`, but the bucket itself is marked **public**, so files are readable by their public URL regardless of RLS. Upload/list/delete still require the service-role key. No file-size or MIME-type restriction is configured.
- **No code in this app currently attaches a Clerk session JWT to a Supabase request** (confirmed by grep — no `getToken`/JWT-template usage anywhere). Every client-side Supabase call in the app (e.g. the old `trip-list.tsx` pattern, now fixed) runs as plain `anon`, and every server-side call uses the service-role key. This is *why* the `cars`-anon-only and `trips`-zero-policies gaps haven't caused visible bugs except the one below: nothing in the app sends an "authenticated" Supabase request today. **Do not add a client-side Supabase query against `trips` using the anon key** — it will silently return nothing. Route any new trips read through a server API route with the service-role key instead (see `app/api/admin/trips/route.ts` for the pattern).
- **Fixed in this session:** `components/admin/trip-list.tsx`'s "Show More Deployments" pagination used to query `trips` directly with the anon key client-side, which returns empty due to the zero-policy RLS above — latent (only 8 trips exist today, fewer than the first page), but would have silently broken as soon as trip count passed 10. It now calls the new `GET /api/admin/trips` route (admin-gated via `requireAdmin()`, service-role key, same car/profile-name joining logic) instead.

**Env vars:** every file now reads the service-role key as `SUPABASE_SECRET_KEY` (the `SUPABASE_SERVICE_ROLE_KEY` outliers in `app/admin/trips/[id]/page.tsx` and `app/admin/users/page.tsx` were fixed — use `SUPABASE_SECRET_KEY` for any new file). `SUPABASE_BUCKET_NAME` is now actually read (falls back to `"car-images"` if unset) in `app/api/cars/route.ts` and `app/api/admin/update-car/route.ts` — use `process.env.SUPABASE_BUCKET_NAME || "car-images"` (or import a shared constant if a third file needs it) rather than hardcoding the bucket name again.

**Registration number handling:** car registrations are always normalized with `.toUpperCase().replace(/\s+/g, "")` before being sent to DVLA or stored — follow this convention in any new code that touches registrations.

**Car compliance/status logic:** "does this car need attention" (MOT not valid, tax not Taxed/SORN, or service overdue) is centralized in `lib/cars/status.ts` (`needsAttention`/`isDriveable`/`isMotValid`/`isTaxValid`/`isServiceOverdue`). This used to be reimplemented separately (and inconsistently) in the dashboard, `AssetIntelligenceCard`, and `DashboardSearch` — always import from `lib/cars/status.ts` instead of reimplementing this check, or the three call sites will drift again.

**Shared UI primitives in `components/ui/`:**
- `Button` (`components/ui/button.tsx`) has a `vault` variant (black-on-orange filled pill, heavy tracked uppercase, glow shadow, hover/active scale) and a `vault-ghost` variant (dark bordered pill) matching this app's actual CTA look — use these instead of hand-rolling `bg-orange-500 text-black rounded-full font-black uppercase ...` inline on every new button. Not every button fits this mold (e.g. the landing page's bespoke glass CTA, or a back-button with a separate icon chip) — don't force a primitive where the design is genuinely one-off.
- `Input` works for `<input>` elements with a `className` override for height/radius/focus-ring (no `Textarea`/`Select` primitive exists yet — those stay as native elements).
- `ErrorBanner` (`components/ui/error-banner.tsx`) is the standard way to surface an async-action failure to the user (`<ErrorBanner message={errorMsg} />`, renders nothing when `message` is falsy) — use it instead of `alert()` or a silently-swallowed error.
- The contact form (`app/contact/actions.ts` + `components/ContactForm.tsx`) is the pattern for a server-action-backed form that needs visible submit feedback: a typed `{ status: "idle" | "success" | "error"; message?: string }` state, driven by React's `useActionState`, rendering a success banner or `ErrorBanner` and disabling the submit button while pending. **Note:** that form does not persist submissions anywhere — no contact-messages table exists in Supabase and no email service is configured, it only `console.log`s server-side. Don't assume it's wired to storage/email; that needs a table or an email provider API key provisioned first.

**Motion/animation conventions — CSS-only, no motion library:** `framer-motion`/`motion`/`gsap` are deliberately not dependencies here (small site, would fight "feels fast"). `tw-animate-css` (already a devDependency) provides the `animate-in`/`fade-in`/`slide-in-from-*`/`duration-*` utility classes used throughout. For scroll-triggered entrances, use the shared `components/Reveal.tsx` (`<Reveal delay={100}>...</Reveal>`, optional `as="section"` prop) — it's `IntersectionObserver`-driven, fires once, and respects `prefers-reduced-motion` (shows immediately via a lazy `useState` initializer rather than inside the effect, to avoid a `react-hooks/set-state-in-effect` lint error — don't move that check back into the effect body). Any new hover/reveal treatment should extend `CarCard.tsx`'s established vocabulary (border-color shift to `orange-500/50` or `/30`, a subtle `-translate-y-1`/`scale-[1.02]` lift, 500-700ms duration) rather than inventing a new one. `components/Hyperspeed.tsx` (the landing-page WebGL background) checks `prefers-reduced-motion` before mounting at all (renders a static gradient instead) and pauses its render loop on `visibilitychange` — follow the same two checks for any other canvas/WebGL effect added later, and keep it behind `next/dynamic(..., { ssr: false })` as done in `app/page.tsx`.

**Image loading:** `lib/image.ts#VAULT_BLUR_PLACEHOLDER` is a small shared blur-up constant (solid `#171717`-tinted SVG data URI) — pass it as `placeholder="blur" blurDataURL={VAULT_BLUR_PLACEHOLDER}` on any new `next/image fill` usage (already used by `CarCard` and `CarGallery`) instead of generating a new one or leaving images to pop in bare.

**Never pass a function as a prop from a Server Component to a Client Component.** React Server Components can't serialize functions (or class instances, Symbols, etc.) across the server→client boundary — doing so throws "An error occurred in the Server Components render" on *every* request, deterministically, with production builds hiding the real message behind an opaque digest. This caused a real production outage on `/cars/[car_id]`: it passed `<CountUp format={(n) => formatPrice(n)} />` where `CountUp` (`components/CountUp.tsx`) is `"use client"`. Fixed by having `CountUp` accept a `format: "number" | "currency"` string prop and resolve it internally instead of accepting a callback — only plain serializable values (numbers, strings, plain objects/arrays) cross the boundary now. If a client component needs custom formatting/behavior controlled from a server-rendered parent, give it a small set of named string/enum variants it resolves internally, never a callback prop.

**Error boundaries exist now — use them as the model for any new one.** `app/error.tsx` (route-level, on-brand "Uplink Interrupted" screen with a retry button) and `app/global-error.tsx` (root-layout-level, renders its own `<html>/<body>` since it replaces the layout). Both are forced `"use client"` by Next's convention, so neither can render the real async `Navbar` Server Component — `app/error.tsx` has its own minimal static header matching the same look instead. Add a route-specific `error.tsx` next to any page where a tailored fallback is worth it; otherwise the root one catches everything.

**Car-detail photo gallery:** lives in `components/CarGallery.tsx` (hover zoom, `IntersectionObserver`-tracked active index) + `components/GalleryDots.tsx` (scroll-position indicator pills) + `components/Lightbox.tsx` (full-screen view, Esc/backdrop/arrow-key nav) — `app/cars/[car_id]/page.tsx` just renders `<CarGallery pictures={pictures} title={title} />`. Deliberately no autoplay and no custom drag-momentum JS (the CSS scroll-snap strip already gives native touch/trackpad snapping) — don't add either without revisiting that reasoning.

**External APIs** (server-side only):
- DVLA Vehicle Enquiry Service (`DVLA_VES_KEY`) — MOT/tax/year lookups by registration. No batch endpoint exists (one registration per call) and DVLA rate-limits per second (`429`). Fleet-wide syncing goes through `lib/dvla/syncFleet.ts`, which fetches with bounded concurrency (`lib/dvla/concurrencyLimiter.ts`, configurable via `DVLA_SYNC_CONCURRENCY`, default `4`) and retries only `429`/`502` with exponential backoff (`lib/dvla/syncFleet.ts#fetchDvlaWithRetry`) — one car's failure never aborts the rest of the fleet. This single function is called by both the manual trigger (`app/api/admin/sync-dvla/route.ts`, admin-only via `requireAdmin()`) and the weekly scheduled trigger (`app/api/cron/sync-dvla/route.ts`, `CRON_SECRET`-gated, invoked by the `vercel.json` cron entry) — don't reimplement the DVLA-calling loop in either route; extend `syncFleet`/`syncOneCar` instead.
- API Ninjas (`API_NINJAS_KEY`) — car spec lookups by make/model/trim, mapped into DB fields via `SPEC_MAP` in `app/api/cars/route.ts`. No batching/rate-limiting layer exists for this one.
- Instagram API (`INSTAGRAM_APP_ID`/`INSTAGRAM_APP_SECRET`) — the **Instagram Login flow** (`graph.instagram.com`/`api.instagram.com`), not the classic Facebook-Page-mediated Graph API, since `@horsepower.vip` has no linked Facebook Page. The live access token (60-day expiry) and the Instagram user id are stored in Supabase's `instagram_token` table, not an env var, since the sync job rotates the token at runtime — seeded once via `app/api/admin/instagram-oauth/route.ts` + `.../callback/route.ts` (an admin clicks "Connect" on `/admin/dashboard`, which redirects through Instagram's own OAuth consent screen). `lib/instagram/syncFeed.ts#syncInstagramFeed` refreshes the token if it's within 7 days of expiry, fetches the latest ~12 posts via `GET /{ig-user-id}/media`, and upserts them into `instagram_posts` (read by `components/InstagramFeed.tsx` on `/home`) — called by both `app/api/cron/sync-instagram/route.ts` (daily, `CRON_SECRET`-gated) and `app/api/admin/sync-instagram/route.ts` (admin-triggered), same dual-trigger pattern as the DVLA sync.

**Styling:** dark-only theme, orange (`#f97316`) accent/primary. Theme tokens are defined in `app/globals.css` (Tailwind v4 `@theme inline`) and documented in `global tags.txt`.
